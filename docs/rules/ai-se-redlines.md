# AI-SE 协作红线（外置条款正文）

> **分类**：AI 协作行为层；索引在 `.codebuddy/rules/00-ai-se-collaboration/RULE.mdc`「外置条款索引」。
> **来源**：移植自 dzmm-nestjs 的 `docs/rules/rule-code-link.md`、`rule-ui.md`、`rule-backend.md`，按 AI-SE（pnpm monorepo / Vue 3 / Express 5 / PostgreSQL / Vitest）适配（2026-11-13）。
> **适用**：动代码 / 排查 / 讲代码链路 / 改 UI / 改接口 / 交付证据 / 要用户验证与汇报。
> **不适用**：纯文档写作（`docs/NN-*.md` 阶段报告、任务书、验收记录）——不加载「代码链路类」「UI 类」「后端·数据·测试类」；「最小范围」「符号删除扫引用」仍适用。
> **优先级**：`AGENTS.md`、`docs/16-vibe-coding-rules.md`、冻结契约与 `AGENTS.md` §9 阶段纪律高于本文件；冲突时报告，不默默对齐。

## 1. 意图与影响面分析

### 意图先复述 + 先读事实再动手

`[P0]` 开工前用一句技术语言复述并**直接执行**，不等待确认；需要用户裁决的点只写一行「待确认：<一句话>」，该点不执行（提问或汇报均可）。排查类任务复述为「在 `XXX` 里定位 `XXX` 的 `XXX` 问题」。

`[P1]` 核心原则：先把与请求直接相关的代码 / 页面 / 配置 / 命名读清楚，再决定怎么做；**不要反问仓库能直接证明的事实**。区分用户目标、用户提出的实现方式、用户对原因的猜测；区分已确认事实、待确认歧义、待确认决策；不得把建议选项伪装成已确认事实。

`[P0]` **禁止猜测后自动执行**：未核实的东西不执行，不配默认后续行为；有现成接口 / 库 / 代码可读的事实，先读先查，不先问。

`[P0]` **讲链路 / 讲机制类提问**（"这个按钮什么时候显示""这个字段从哪来""流程是什么""为什么这样写"）：只陈述**代码原文**——判定条件原文 + 触发链 + 生命周期（谁赋值、谁清空）。禁止推演、禁止列可能性、禁止顺带解释现象、禁止为已知结论再找验证。

`[P0]` **指令即方法**：用户附带操作指令（"直接告诉我 X""不需要思考"）时直接执行，不重建方法、不加推理铺垫、不先列候选方案再选。

`[P0]` **是非提问只回答有无**：问「有没有 X」→ 读代码答「有 N 处（行号）/ 没有」；没有就直接补上，并给出复现与回贴步骤。不自行造样本（curl / 拉产物 / 模拟请求头 / sleep 复查），用户说「我来看」即停。

### 决策点记录 / 开工不需要闸门

`[P0]` **排查类请求不适用本节**，第一动作走「排查铁律——取证优先于推理」。开发类需求出现以下情况时不停下来问，写成一行「待确认：…」，该点不执行：

- 同一句话存在两种以上合理解释，且会产生不同的用户可见行为（"删掉 mock"是删函数还是连弹窗一起删）。
- 用户目标与其指定的实现方式互相冲突。
- 需要新增技术选型、依赖或接口约定才能继续。
- 涉及 PostgreSQL 表结构变更但迁移方式未确认。
- "这里""全部""统一""同样处理"等指向不明，且会改变修改范围。

`[P0]` **开工不需要闸门**：能一句话说清范围更好；说不清就以「待确认」记录，不阻塞其余开工。**但 `AGENTS.md` §9 阶段纪律优先**：一次任务只做一个已命名阶段 / 子阶段，做完即停；「待确认不阻塞」仅限同一阶段内，不得据此自动推进下一阶段。

### 影响面分析

`[P0]` **本仓库路径**：前端 `apps/web/src/`（`views/`、`viewmodels/`、`stores/`、`api/`、`components/`、`composables/`）；后端 `apps/server/src/`（`routes/`、`services/`、`index.ts` 组合根）；跨包契约 `packages/shared/src/`；迁移与存储 `packages/database/src/`；其余能力 `packages/<pkg>/src/`；文档 `docs/`。改动前先判断目标属于前端 / 后端 / 共享包 / 跨端。

`[P2]` **输出格式**：每个修改动作带 `[类型标签]` + 具体名称，多步骤编号列出。

> 1. 改 `WorkflowDetailView`，[新增组件] 审批操作条 + [新增接口调用] `POST /api/approvals/:id/approve`，实现详情页审批
> 2. 改 `routes/workflows.ts`，[新增端点] `GET /api/workflows/:id/trace` + 改 `services/workflowService.ts`，[新增函数] `getTrace`，实现追踪数据查询
> 3. [新建完整业务组件] `ApprovalDialog`，预估 120 行，props: { approvalId, taskTitle }，emits: { confirm, cancel }，实现审批确认弹窗

**排查类**：定位到具体函数名，不泛泛说"搜索不生效"；定位后补充修改动作。

`[P2]` **类型标签（AI-SE 专属）**

| 类别 | 标签 |
| --- | --- |
| 前端 Vue | `[新增视图]` / `[新增组件]` / `[修改DOM]` / `[删除DOM]` / `[新增store]`（Pinia）/ `[新增组合式函数]`（`useXxx.ts`）/ `[新增ViewModel]` / `[修改样式]`（Tailwind class）/ `[新增路由]` |
| 接口 | `[新增接口调用]` / `[修改接口调用]`（`apps/web/src/api/`）/ `[新增端点]` / `[修改端点]`（写明 HTTP 方法 + 路径 + `routes/<资源>.ts`）/ `[修改契约]`（`packages/shared` 类型 / Zod schema / 冻结契约） |
| 数据 | `[新增迁移]`（`packages/database` SQL）/ `[修改存储]`（Pg* store） |
| 测试 | `[新增测试]`（`apps/web` 一律 `src/__tests__/`；其余包跟随所在包既存惯例） |
| 工程类（需用户确认） | `[新增依赖]` / `[修改配置]`（`pnpm-workspace.yaml`、`tsconfig.base.json`、`eslint.config.mjs`、Vite / Docker 配置） |

`[P0]` **免确认豁免**：简单显示类 UI 改动（元素显隐、文案、样式、单字段展示）、一套完整功能的新增 DOM、日志增删改 → 复述后直接执行。**不在豁免内**：删除 / 替换 DOM、交互降级、接口契约删改 → 按「UI/DOM 与契约变更红线」单独列出，等用户对该动作本身的明确确认。

`[P2]` **根据影响面路由**：1–2 个文件且方式明确 → 复述后直接执行；跨端改动（`apps/web` ↔ `apps/server` ↔ `packages/*`）→ 接口约定（路径、入参、返回结构）必须在复述中先确认；影响面较大 → 先在 `docs/NN-<主题>.md` 写任务书再实施（沿用 `AGENTS.md` §9）。

## 2. 代码链路类

### 最小范围

`[P0]` 只改已确认意图必需的部分，相邻问题可以报告，不得顺手修复。不得主动增加新功能 / 新依赖 / 新组件 / 无关重构 / 范围外修改（含其他端、其他包）。与 `AGENTS.md` §9「禁止顺手完善相邻功能」同义，二者取严。

### 源头冲突时以事实为准

`[P0]` 接口返回数据 / 用户回贴日志 / `trace` 与 `tool_calls` 记录 = 事实，代码与之冲突则改代码、不疑数据；怀疑环境跑旧版，或想用「缓存 / watch 未生效 / 刷新试试」解释现象时，无版本、截图或代码凭据不得归因外部，也不得先叫用户重载刷新。

### 排查铁律——取证优先于推理

`[P0]` **触发**：为什么 / 为啥 / 怎么 / 如何 / 原因 / 怎么回事 / 哪里出问题 / 不生效 / 不显示 / 报错 / 失效 / 没带上 / 帮我看看 / 查一下等，凡指向"找出原因、定位问题"的提问，**第一优先级一律不是推理**——不列候选原因、不建假设链、不分析时间线。第一动作固定为：

1. `[P0]` 沿链路补埋点 / 取日志。AI-SE 可用取证点：server pino 日志、`GET /api/workflows/:id/trace`（端到端追踪）、`GET /api/metrics`、`workflow_events` / `tool_calls` / `agent_runs` 表、`apps/web/src/api/` 请求与响应、Playwright 截图、Vitest 复现用例。链路按「发送端 → 传输 → 接收端 → 拼装点」逐段布点。
2. `[P0]` 给用户明确取证步骤（复现操作 + 回贴哪些日志行）。
3. `[P0]` 结论只能来自回贴证据或实验观察与代码的**逐点对照**，不来自推断。

`[P1]` 本项目**没有** dzmm 的 `diagnose-issue` / `report-change` 等 Skill，不得引用或尝试加载它们；取证动作按上述清单直接执行。

- `[P0]` 用户附带操作指令（"看链路加日志""不需要思考"）时，指令即方法，直接执行。
- `[P0]` **例外封死**：「上下文都在 / 刚经历过同一链路 / 代码刚才读过」不构成例外；唯一例外 = 用户明说「直接推理 / 不用取证」。
- `[P0]` **改名封死**：判定按本质不按措辞——推演改名为「想想事实链 / 机制核对 / 已有代码分析」同样违规；合法输出仅「原文引用 + 直接对照」。
- `[P0]` **链路说明前置**：上下文已有链路材料（日志 / 查询结果 / 刚读的代码）时，回复固定以「链路说明」块开头，块内只三行——`原文引用：<代码 / 日志 / 数据原文 + 出处>`、`直接对照：<数量 / 有无交集 / 时间戳先后>`、`矛盾点：<照抄，不解释>`；块内夹带因果句即违规。用户回贴前不得进入原因分析。
- `[P0]` **单矛盾单取证**：为一个矛盾最多发起 1 次取证；取证后仍矛盾 → 直接输出矛盾本身，不换角度再取。

### 用户操作即事实

`[P0]` 用户报告「我点了 / 我操作了」= 操作已发生——Web 控制台日志看不到时必须从埋点 / 交互设计找原因，**不得以「日志没有」否定用户操作**。交互组件禁止 disabled 静默拦截（点击无反应无日志 = 用户侧纯黑盒），必须视觉灰化（opacity + cursor）+ 点击必有 toast / 日志反馈；埋点须覆盖弹窗打开 / 勾选 / 按钮禁用状态等前置环节。

### 接口字段以契约源为准

`[P0]` 新增 / 修改接口调用前必须取契约源——`apps/server/src/routes/*` 的请求 / 响应定义、Zod schema、`packages/shared/src/` 导出的类型、`packages/database/src/` 的迁移与表结构、冻结契约（如 `docs/25-mcp-contract-freeze.md`）、`apps/web/src/api/*`；**不得以代码注释或既有实现自证作为依据**；字段名、可空性、类型一律以契约原文为准。与冻结契约冲突时按 `AGENTS.md` §9 报告 CONTRACT CONFLICT，不悄悄放宽。

### 符号删除 / 改名 / 移动必须同步扫引导语

`[P1]` 删除、改名或移动函数 / 变量 / 组件 / 文件 / 端点时，必须同步检索并更新引用处（调用方、注释、`docs/NN-*.md` 任务书与验收清单、`packages/shared` 类型、`migrate.test.ts` 的文件清单断言、共享 fixture 的逐字段断言），改完复查一次残留。

### Git 排障先问「操作前状态 + 目标」

`[P1]` 用户以「rebase 之后工作区乱了」「git 搞乱了」求助时，动手前只问两个用户一定能答的问题——①你想达成什么（提交 / 丢弃 / 保留哪些改动）②现在缺什么；**不得问**「这堆文件是谁的 / 要不要保留」这类用户答不出的问题。

## 3. UI 类（`apps/web`）

### UI/DOM 与契约变更红线

`[P0]` 对 `.vue` 业务组件、关键 DOM（弹窗、表单、表格列、操作按钮）或 `packages/shared` 中关键接口契约 / 数据结构执行删除 / 替换 / 交互降级（选择器改手动输入、接口字段静默变更等），必须同时满足：

- 影响面复述中以 `[删除DOM]` / `[修改DOM]` / `[修改契约]` 标签单独列出该动作，不与其他动作合并表述；
- 用户对该动作本身有过明确确认；
- 因依赖被删导致的编译报错不构成删除理由——保留组件 + 报告依赖断裂 + 询问处理方式；
- 执行中若需推翻自己在影响面复述中承诺的范围边界（如"不改 UI"），视为新决策点，停下确认，不得静默调整。

### 禁止嵌套滚动

`[P0]` 任何 UI 改动**一律不得嵌套滚动**——只允许一层滚动容器，已有滚动容器内不得再套第二层（Tailwind `overflow-y-auto` 套 `overflow-y-auto`、`max-h-*` + `overflow` 套滚动容器等任意形式）。判据＝同一区域内是否出现第二层滚动容器。用户明确主动要求时才可用；不得以"防撑爆""表格太宽""内容太长"为由自行加上。

### 四态齐全

`[P0]` 新写或改动列表 / 请求 / 弹窗 / 表单提交（含 `views/` + `stores/` + `api/` 链路）时，必须同时具备 **loading**（请求在途）/ **空态** / **错误态** / **有数据态**；空态不得在请求在途时渲染（否则用户会误以为真的没有数据）。

## 4. 后端·数据·测试类

### 数据库模型与迁移

`[P0]` 迁移在 `packages/database/src/`。新增 / 修改 SQL 迁移须遵循 `AGENTS.md` §7 风格（`CREATE TABLE IF NOT EXISTS`、`gen_random_uuid()`、每表一个 `set_updated_at()` 触发器、唯一键 `NULLS NOT DISTINCT`、PG16），并扩展 `migrate.test.ts` 的文件清单断言；改动后提醒用户执行 `corepack pnpm --filter @ai-se/database migrate`，并说明迁移方式待确认时该点不执行。

### 接口契约同步

`[P1]` 新增 / 修改端点时按 `AGENTS.md` §4 落地：`routes/<资源>.ts` + `services/<资源>Service.ts` + `index.ts` 组合根；同步检查 `apps/web/src/api/` 的 fetch 调用与 `packages/shared` 类型是否需要更新；跨端改动先在影响面复述中列出。字段名 / 可空性 / 类型以契约源为准。

### 验证命令与构建产物

`[P1]` 每完成一个包改动跑 `corepack pnpm --filter @ai-se/<pkg> typecheck && lint && test`；阶段收尾跑全仓 `corepack pnpm -r run typecheck && lint && test`。新增业务逻辑必须带测试，核心链路（真实连接 / 真实协议 / 真实迁移）不允许全 mock 代替。

`[P2]` 各包 `dist/`、`node_modules/` 不纳入 review 与 commit-message 范围；`pnpm-lock.yaml` 变更须与依赖变更同批说明。

`[P1]` 后端配置、环境变量与选型沿用 `AGENTS.md` §1 / §10，不在本文件复述。

## 5. 沟通类

### 汇报口径：结论先行，技术折叠

`[P0]` 第一段只写「用户会看到什么变化」，不写改了哪个函数 / 文件；文件、行号、判据、证据放最后一段或省略。判定词落到用户能看见的事实（「列表里出现第 3 条记录」），不写「静态可证」「闭环」。

`[P1]` **例外**：阶段交付报告仍按 `docs/16-vibe-coding-rules.md` 的固定 11 节（Modified Files、Implementation、…、Next Phase Boundary）输出；本节约束的是日常对话汇报，二者不冲突。

### 要用户验证时：屏幕视角五段

`[P0]` 触发：我请用户去点 / 看 / 确认；用户问「我要怎么验证」；我说某条「未验证 / 需要你确认」。输出五段，缺一段不许发：

1. **在哪**：页面地址或页面名（`http://localhost:5173` 的 Workflows 详情页；`http://localhost:3000` 的 `GET /api/metrics`）
2. **前置条件**：`corepack pnpm dev` 是否已跑、Docker Postgres/Redis 是否就绪、`LLM_PROVIDER` 用 mock 还是真实凭据、是否需要特定 fixture / 已有 Workflow 数据
3. **动作**：编号步骤，一步一个动作，只用屏幕上看得见的文字（例：点「Start」）
4. **算对的样子**：一句可判定的现象（例：状态从 PENDING 变成 RUNNING，事件时间线多出 2 行）；特定数据下不出现属正常的，当场写明
5. **不对时怎么回贴**：一句话（把页面截图发我，或贴 server 日志那几行 / `trace` 片段）

模板内禁止出现：变量名 / 函数名 / 常量名 / 文件名 / 行号 / 接口字段名、内部术语（契约、幂等、门控、落库）、缩写黑话。用编号当主语必须紧跟人话名字。发稿自检：不看代码知道点哪吗？知道在哪个页面、什么前置条件吗？知道看到什么算做对吗？

### 说「验不了 / 做不了 / 缺环境」时：四件事

`[P0]` 必须写全：①哪个页面 ②什么账号或条件下才看得到（并说明**现在是正常现象还是缺陷**）③是我没权限还是功能有问题 ④需要用户做什么，或我如何记录。AI-SE 常见缺环境：`LLM_PROVIDER` 无真实凭据、Docker Postgres/Redis 未启、GHCR / 远程仓库凭据缺失、Sandbox 不能挂 Docker socket。禁止只给结论。

### 一次一件事，别把该我做的活派给用户

`[P1]` 验证说明给编号步骤，一步一个动作且每步带预期现象；要用户决策时，选项必须是用户能判断的东西（要不要这个效果），不是实现方案 A/B/C；先自证——读代码 / 读日志 / 跑脚本能确认的不找用户。只有三类才请用户动手，且一句话说明为什么只能他做：**需要真实账号或权限、需要真实业务数据、需要人眼判断画面**。

### 反例库（改法照抄）

| 场景 | 说错的话 | 改法 |
| --- | --- | --- |
